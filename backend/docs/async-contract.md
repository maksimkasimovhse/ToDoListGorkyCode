# Асинхронный контракт Go, фронта и ML

Этот документ уточняет транспорт из `contracts (1).md` для Redis Streams и polling.
Исходные внешние документы не изменены. Версия конверта Redis — 1.
Модель только разбирает текст; записи, проверки и итоговый ответ — ответственность Go.

## HTTP

`POST /api/message` принимает сообщение:

```json
{
  "client_message_id": "client-001",
  "session_id": "tab-001",
  "text": "Поставь встречу с Иваном завтра",
  "input": "text",
  "timezone": "Europe/Moscow",
  "choice": null,
  "context": {"selected_item_id": null}
}
```

`input`: `text` или `voice`. Для голоса фронт присылает уже распознанный текст.
Вместо текста можно передать `choice: {"option_id":"yes"}`; тогда `text` отсутствует или null.
Часовой пояс пока передаётся в сообщении, по умолчанию Europe/Moscow.
Входная структура проверяется строго; неизвестные поля отклоняются. Размер тела до 64 КиБ,
текст до 16000 байт, идентификаторы клиента и диалога — до 128 байт.

Успешный приём возвращает `202 Accepted`, заголовок `Location: /api/messages/{message_id}`:

```json
{
  "message_id": "c5bc2943-4789-42dd-9a85-a3d8128dd235",
  "status": "processing",
  "response": null,
  "created_at": "2026-10-30T12:00:00Z",
  "deadline_at": "2026-10-30T12:00:15Z"
}
```

`202` подтверждает сохранение сообщения и outbox в PostgreSQL, а не выполнение команды.
Фронт вызывает `GET /api/messages/{message_id}` примерно раз в секунду до завершения.
Этот GET возвращает `200` с такой же обёрткой и полем input_token (null вне ожидания ввода).
Состояния сценария:

- `processing`: выполняется обработка, обычный ввод заблокирован;
- `awaiting_input`: response содержит clarify; открывается окно ввода полей;
- `awaiting_confirmation`: response содержит confirm; открывается окно подтверждения;
- `completed`: действие завершено, response содержит done, results или info;
- `failed`: сценарий завершился с error;
- `cancelled`: пользователь отменил сценарий.

Обычный ввод разблокируется только при completed/failed/cancelled. Во время ожидания поля
или подтверждения диалог остаётся занят. Во время ожидания ввода транзакция БД не открыта.

`response` сохраняет общую форму прежнего контракта: `type`, `reply`, `speak`, `items`,
`options`, `data`, `undo_token`, `suggestions`. Уточнение не завершает сообщение: исходный
message_id сохраняется до конца всего сценария. Обычный POST /api/message не используется
для продолжения. Подробный HTTP-контракт формы: [сценарий диалога](dialogue-flow.md).

Повтор того же client_message_id в том же диалоге с тем же содержимым возвращает прежний
message_id: `202` при processing, иначе `200` с актуальным статусом. Повтор с другим
содержимым — `409 idempotency_conflict`. Новое сообщение в занятом диалоге —
`409 conversation_busy`; оно не сохраняется. Диалог занят при processing, awaiting_input
и awaiting_confirmation. Разные диалоги работают параллельно.

`GET /api/history?session_id=tab-001` возвращает `{history: [...], pending_messages: [...]}`.
В истории — до 100 последних сообщений пользователя с ответами ассистента. После
перезагрузки страницы фронт восстанавливает сообщения: для processing продолжает polling,
для awaiting_input/awaiting_confirmation восстанавливает окно с актуальным input_token.
Ожидающие ввода сценарии тоже присутствуют в pending_messages.
Отключение фронта не отменяет обработку принятого сообщения.

Ошибки приёма и polling: `400 validation`, `404 not_found`, `409` как выше, `500 internal`.
Формат: `{ "error": { "code": "...", "message": "..." } }`.
Ошибки уже принятой команды возвращаются внутри сохранённого response при polling.

## Redis

По умолчанию:

| Назначение | Stream | Consumer group |
|---|---|---|
| Go → ML | planner:ml:requests | создаёт ML, например planner-ml |
| ML → Go | planner:ml:results | planner-backend |

Одна запись Stream содержит поле `payload` со строкой JSON. Streams предназначены для
этих двух групп; Go удаляет обработанные результаты после ACK. Для восстановления после
сбоя Go забирает результаты, не подтверждённые другим обработчиком более 30 секунд.

Задание модели:

```json
{
  "version": 1,
  "message_id": "c5bc2943-4789-42dd-9a85-a3d8128dd235",
  "attempt_id": "d0135f42-2511-48c9-b061-ed8c96c76d49",
  "deadline_at": "2026-10-30T12:00:15Z",
  "request": {
    "text": "Поставь встречу с Иваном завтра",
    "now": "2026-10-30T15:00:00+03:00",
    "timezone": "Europe/Moscow",
    "anchors": {
      "today": "2026-10-30",
      "tomorrow": "2026-10-31"
    },
    "history": [],
    "expects": null,
    "draft": null,
    "focus": null,
    "candidates": null
  }
}
```

anchors здесь сокращены. Реальное задание также содержит weekday, day_after_tomorrow,
this_week, next_week, last_week, this_weekend, month_end, next_weekday и following_week_weekday.
now и anchors фиксируются при приёме сообщения; при повторной попытке они не меняются.
В request также может присутствовать choice.

Для уточнения draft содержит intent, params, source_text, missing, attempt, expires_at.
Для подтверждения добавляется pending_actions. Продолжение из формы обрабатывается напрямую
в Go через /answer, без нового задания модели.

Ответ ML публикуется в поток результатов с теми же message_id и attempt_id:

```json
{
  "version": 1,
  "message_id": "c5bc2943-4789-42dd-9a85-a3d8128dd235",
  "attempt_id": "d0135f42-2511-48c9-b061-ed8c96c76d49",
  "result": {
    "status": "needs_clarification",
    "actions": [{
      "intent": "create_meeting",
      "params": {"title":"Встреча с Иваном", "date":"2026-10-31", "time":null}
    }],
    "missing": ["time"],
    "question": "На какое время поставить встречу?",
    "options": []
  }
}
```

Готовая команда: status ready и те же actions с заполненными полями. Дата и время
передаются отдельно: date YYYY-MM-DD, time/end_time HH:MM. Для list/search границы
from/to — RFC3339 со смещением, интервал полуоткрытый [from,to).

Команда answer используется внутри Go для продолжения; фронт передаёт поля в /answer,
а не новое текстовое сообщение. Повторный разбор моделью не требуется.
Непонятный запрос: `{"status":"not_understood","actions":[]}`.
Ошибка ML: внешний конверт с `error: "llm_unavailable"` и `result: null`.
question модели не исполняется: Go формирует собственный вопрос по недостающему полю.

Порядок работы ML:

1. Создать группу чтения заданий с начальной позицией `0`, чтобы не потерять уже накопленные задания.
2. Читать через XREADGROUP, восстанавливать неподтверждённые задания после сбоев.
3. Проверять deadline_at перед запуском дорогого вычисления.
4. Опубликовать результат, затем подтвердить задание через XACK; по возможности выполнить
   XADD результата, XACK и XDEL задания в одной Redis-транзакции.
5. Не удалять задания и не обрезать поток до успешной публикации результата.

Повтор задания с тем же attempt_id допустим. ML желательно переиспользовать результат;
Go повторно не выполняет сохранённую команду. Для неверной структуры ответа Go создаёт
одну повторную попытку с новым attempt_id и тем же общим deadline_at. После второй ошибки
сохраняет llm_bad_output. Ответ старой попытки игнорируется.

## Надёжность и состояние

Сообщение и outbox создаются одной PostgreSQL-транзакцией. Публикация в Redis может
повториться после сбоя между XADD и фиксацией published_at; идентификатор попытки сохраняется.
Применение команды, ответ, история и состояние диалога фиксируются другой общей транзакцией.
Сбой записи откатывает изменения; подтверждение об успешном действии не формируется.

Черновик, история и фокус хранятся в PostgreSQL. Redis используется для обмена заданиями
и результатами. История контекста ограничена десятью репликами, срок черновика — десять минут.
Сообщения, результаты и outbox пока автоматически не удаляются из PostgreSQL.

MESSAGE_TIMEOUT по умолчанию 15 секунд, включая ожидание в очереди и повторную попытку.
Просроченная обработка завершается с llm_unavailable. После перехода в ожидание ввода
deadline_at обозначает срок черновика: по истечении сохраняется failed с input_timeout,
черновик сбрасывается и диалог разблокируется. Поздний результат не меняет записи.
Некорректный конверт без пригодных идентификаторов журналируется и удаляется; связанное
сообщение, если оно было, завершится по тайм-ауту.

## Реализованный объём

- Ручное создание и чтение task/reminder/meeting, список и поиск по словам.
- Команды create_task, create_reminder, create_meeting, list, search, answer, cancel, help, unknown.
- Составные команды из нескольких create_* выполняются атомарно.
- Уточнения обязательных полей, подтверждение прошедшего времени и точного дубликата по названию/дню.
- Сроки задачи: дата, точный момент, период или отсутствие срока.

Пока используется один демопользователь с фиксированным UUID; идентификатор владельца
не принимается от фронта или модели. Авторизация и профили ещё не реализованы.
Смысловой поиск не подключён: search явно возвращает semantic false и предупреждение
о поиске по словам. Эмбеддинги и их транспорт нужно согласовать с ML отдельно.
Ручное изменение/выполнение/удаление и проверка конфликтов встреч реализованы. Изменение и удаление через модель, повторы, уведомления и внешний календарь пока не реализованы.
Связанные напоминания через for_meeting пока отклоняются.
Список поддерживает явные from/to; дополнительные kind next/free_check пока не реализованы.

Конфликт встреч возвращается через confirm с data.reason = meeting_conflict и списком data.conflicts.
Подтверждение использует /answer и input_token. См. [FR-11](meeting-conflicts.md).
