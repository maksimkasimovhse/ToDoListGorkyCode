# Вход пользователей и сессии

## Тестовые аккаунты

Миграция 00004_create_users.sql создаёт таблицы users и message_sessions и два тестовых аккаунта:

| Логин | Пароль |
|---|---|
| demo1 | DemoPass1! |
| demo2 | DemoPass2! |

Это аккаунты локального прототипа. Для публичной установки замените/отключите их и включите HTTPS.
У demo1 прежний UUID демопользователя, поэтому существующие демозаписи остаются у него.
Данные items и conversations миграция не переписывает. Старые миграции не изменены.
Регистрация, гостевой доступ и смена пароля пока не реализованы.

## HTTP

Публичны только файлы фронта, GET /healthz и POST /api/auth/login:

```http
POST /api/auth/login
Content-Type: application/json

{"login":"demo1","password":"DemoPass1!"}
```

Ответ 200: {"token":"секретный Bearer-токен","user":{"id":"UUID","login":"demo1","timezone":"Europe/Moscow"},"expires_at":"RFC3339"}.

Для всех зарегистрированных бизнес-маршрутов (items, message, messages, history),
GET /api/me и POST /api/auth/logout требуется заголовок:

```http
Authorization: Bearer <token>
```

GET /api/me возвращает id/login/timezone, settings и now. POST /api/auth/logout удаляет текущую
сессию из Redis и возвращает 204. Другие сессии того же пользователя остаются действительными.
Передавать токен в query-параметрах нельзя. Фронт не отправляет токен в URL SSE.
Без авторизации больше нет автоматического доступа под демопользователем.
Сессия авторизации и session_id диалога — разные сущности.

Ошибки:

- 401 invalid_credentials — неверные данные входа, одинаковый ответ для неизвестного логина и пароля;
- 401 unauthorized — нет токена, неверный токен, истёкшая/отозванная сессия или неактивный пользователь;
- 429 too_many_attempts — более 20 попыток входа с одного IP за минуту;
- 503 auth_unavailable — PostgreSQL/Redis не позволяют проверить авторизацию; доступ не предоставляется;
- 404 not_found — чужая запись/сообщение неотличимы от отсутствующих.

## Как проверяется вход

SELECT id,login,timezone,password_hash,is_active FROM users WHERE login=$1.
Запрос параметризован. Логин приводится к нижнему регистру и очищается от крайних пробелов.
Пароль не сравнивается в SQL и не хранится открытым. В Go сравнивается хеш
PBKDF2-HMAC-SHA256 (600000 итераций, соль 16 байт, результат 32 байта, constant-time compare).
Для неизвестного логина выполняется такая же по стоимости проверка.

Используется стандартный [crypto/pbkdf2 Go](https://pkg.go.dev/crypto/pbkdf2);
параметры PBKDF2 описаны в [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2).

После проверки создаётся случайный токен из 32 байт. В Redis сохраняется только его SHA256:

```text
planner:auth:session:<sha256-token> → {user_id, expires_at}
```

Создание выполняется одним SET NX с TTL. SESSION_TTL по умолчанию 168h (7 дней).
Срок фиксированный, запросы его не продлевают. Проверяется также абсолютный expires_at.
На каждом защищённом HTTP-запросе middleware читает Redis и делает SELECT пользователя по id,
проверяя is_active. user_id для бизнес-логики берётся только из этой сессии.

## Асинхронная обработка

При приёме сообщения message_sessions сохраняется вместе с messages и outbox в одной транзакции:
message_id, user_id, хеш токена и expires_at. Открытый токен и сведения авторизации не отправляются ML.

Перед выполнением ответа ML проверяются сессия Redis, срок и активность пользователя.
Перед фиксацией результата проверка повторяется. Если сессия отозвана/истекла в ходе операции,
изменения откатываются до savepoint, а сообщение завершается failed с кодом session_expired.
Клиент после повторного входа может получить эту ошибку через polling/историю и отправить новый запрос.
Для старых processing-сообщений без привязки сессии выполнение также запрещается.

Для уже сохранённого choose/clarify/confirm текущий владелец может войти заново и продолжить
через /answer с действующим токеном авторизации и прежним input_token, пока не истёк сам черновик.
input_token защищает конкретный шаг диалога и не заменяет авторизацию.

## Подключение фронта

Форму входа/выхода и обработку 401 реализует фронтендер. Серверная часть готова:
POST /api/auth/login возвращает token/user/expires_at; бизнес-запросы требуют Authorization: Bearer.
POST /api/auth/logout отзывает текущую сессию, GET /api/me возвращает профиль.
При 401 клиент должен остановить polling и предложить повторный вход.
Пароль не сохранять; токен не передавать в URL. Отдельной формы авторизации в текущем фронте нет.
