# Выбор записи для изменения (текст и голос)

И текст, и распознанный голос поступают в POST /api/message. ML возвращает действие update,
complete или delete с target. Бэкенд сам ищет записи своего пользователя и выполняет операцию по id.
Название не обязано быть уникальным. Поиск пока остаётся по подстроке, без смыслового сопоставления.

## Команды ML

Перенос встречи:

```json
{
  "status": "ready",
  "actions": [{
    "intent": "update",
    "params": {
      "target": { "ref": "filter", "participant": "Иван", "types": ["meeting"] },
      "changes": { "date": "2030-01-05", "time": "16:00" }
    }
  }]
}
```

В target поддерживаются:

- ref filter: query, participant, types, from/to (RFC3339), status. Пустой фильтр запрещён.
- ref focus: запись из серверного фокуса, включая context.selected_item_id от фронта.
- ref candidate, numbers [2]: вторая запись из последнего списка, переданного Go в request.candidates.

Произвольный id из результата ML не используется. all true и массовые изменения не поддерживаются.
Для встреч статус scheduled/cancelled; open/done относятся к задачам и напоминаниям.

update принимает непустой changes: title, date, time, shift_min, duration_min,
participants_add, participants_remove, clear_due. Дата и время задаются отдельно в часовом поясе
сообщения. При переносе сохраняются длительность и отступ напоминания.
Смену типа и изменение срока-периода этим контрактом пока выполнить нельзя; используйте ручной API.
Для записи без срока при назначении времени нужна дата. Неизвестные поля и null отклоняются.

complete: params {"target": {...}, "done": true} — выполнить; done false — вернуть в работу.
delete: params {"target": {...}} — мягкое удаление после отдельного подтверждения.

## Как выбирается запись

Нет совпадений — info/not_found, ничего не меняется. Одно совпадение — применяется update/complete;
для delete сначала confirm. Несколько — response.type choose, статус сообщения awaiting_input:

```json
{
  "type": "choose",
  "reply": "Подходит несколько записей. Какую выбрать?",
  "items": [],
  "options": [{ "id": "UUID-показанной-записи", "label": "1. Встреча с Иваном — 2030-01-05 16:00" }],
  "data": { "expects": "item", "pending_intent": "update", "total": 2, "shown": 2 }
}
```

В реальном ответе items содержит полные объекты Item; пример выше показывает только формат.
Показывается не больше 20 записей. При большем числе совпадений сервер сообщает total/shown
и предлагает отменить сценарий и уточнить исходный запрос. Скрытые кандидаты не выбираются автоматически.

Выбор кнопкой:

```json
{ "input_token": "актуальный-токен", "option_id": "UUID-из-response.options" }
```

Выбор текстом или распознанным голосом:

```json
{ "input_token": "актуальный-токен", "text": "вторую" }
```

Оба варианта отправляются в POST /api/messages/{message_id}/answer.
Поддерживаются цифры и простые русские числительные/порядковые номера 1–20, например
«номер два», «вторую встречу», «третью задачу». Нечёткий выбор по названию не выполняется:
сервер возвращает 400 validation и сохраняет ожидание. Выбирать можно только показанную запись.
Выбор не требует нового задания ML. Нельзя смешивать выбор с изменением полей или confirmed.

Бэкенд перечитывает запись и проверяет владельца и updated_at. Если запись изменилась или удалена,
возвращается обновлённый choose с новым токеном, даже если остался один кандидат.
Пользователь выбирает заново; сервер не подставляет другую запись молча.
После выбора update/complete возвращает done, delete — confirm. После явного «да» удаление выполняется.

При конфликте переноса встречи возвращается confirm с data.reason meeting_conflict.
«Нет» переводит в clarify/time, «да» разрешает показанные пересечения; новые конфликты требуют
нового подтверждения. Обработка выполняется под общей блокировкой расписания пользователя.

Черновик выбора и исходное действие хранятся в conversations.state. Поля response и input_token —
в messages. После перезагрузки окно восстанавливается через /api/history. Действуют прежние правила
тайм-аута, /cancel и идемпотентности токенов. Миграция схемы не требуется: используется awaiting_input.

## Фронтенд

choose рисуется как нумерованные карточки и кнопки. Кнопка посылает option_id в /answer,
текст/голос — text в тот же маршрут. «Отмена» вызывает /cancel. После done обновляется список записей.
