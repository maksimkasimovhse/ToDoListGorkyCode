# FR-11: конфликты встреч

Конфликт — строгое пересечение интервалов: `existing.start_at < end_at AND existing.end_at > start_at`.
Интервалы полуоткрытые `[start_at, end_at)`: конец одной встречи может совпадать с началом другой.
Сравниваются точные моменты времени с учётом UTC-смещения. Встречи на весь день используют те же правила.
Учитываются только `meeting` со статусом `scheduled`, принадлежащие текущему пользователю,
без `deleted_at`. При изменении запись не конфликтует сама с собой.

## Ручной API

При `POST /api/items` и переносе/восстановлении встречи через `PATCH /api/items/{id}`
сервер до сохранения проверяет расписание. При пересечении возвращает HTTP 409:

```json
{
  "error": {
    "code": "meeting_conflict",
    "message": "Время пересекается с другими встречами.",
    "conflicts": ["здесь полные объекты Item"]
  }
}
```

`conflicts` содержит реальные объекты записей; строка выше — только обозначение их места.
До подтверждения запись не создаётся и перенос не сохраняется. Фронт показывает список
и предлагает отменить действие, выбрать другое время или сохранить с пересечением.
Для сохранения повторить исходный POST/PATCH с `"allow_conflicts": true` в теле.
Это явное разрешение сохранить пересечения, существующие на момент повторного запроса.
При создании ответ — 201 с записью, при изменении — 200.
Для нового времени без разрешения пересечений нужно убрать allow_conflicts или передать false.
`409 item_conflict` — отдельная ошибка устаревшей версии записи, а не пересечения времени.

Изменение только названия/участников не требует повторно подтверждать уже разрешённое пересечение.
Изменение времени или возврат cancelled → scheduled проверяется заново. Отмена и удаление
освобождают время. Тип записи менять по-прежнему нельзя.

## Диалог с моделью

Для `create_meeting` используется существующее состояние `awaiting_confirmation` и ответ `confirm`:

- `response.data.reason`: `meeting_conflict`;
- `response.data.conflicts`: конфликтующие записи;
- `response.items`: те же записи для отображения;
- `response.options`: yes/no;
- `input_token`: актуальный токен окна.

Подтверждение — `POST /api/messages/{id}/answer` с input_token и confirmed, без повторного вызова ML.
При confirmed: false конфликтное время отклоняется, но черновик сохраняется: сервер возвращает
awaiting_input и вопрос «Хорошо. На какое время поставить?». Новый input_token используется
для /answer с time (при необходимости также date). Длительность, название и прочие поля сохраняются.
После ввода времени конфликты проверяются заново. Отдельная отмена всего действия — через /cancel.
При нескольких действиях вопрос указывает название изменяемой встречи; остальные действия сохраняются
в черновике до атомарного завершения всей команды. Для нескольких create_* проверяются также пересечения между
предлагаемыми встречами; до подтверждения не сохраняется ни одна запись, включая задачи.
У ещё не сохранённых встреч в списке конфликтов нет id.

При подтверждении расписание проверяется снова. Если появилась новая конфликтующая встреча
или изменилась ранее показанная, сервер возвращает новое окно с новым input_token.
Повторное подтверждение с тем же токеном обрабатывается существующим механизмом идемпотентности.
Перенос через update от модели также проверяет конфликты после выбора записи. См. selection.md.

## Транзакции и проверка

Проверка и запись выполняются в одной транзакции под PostgreSQL advisory lock по пользователю.
Ручные операции и обработка результатов ML используют одну блокировку, в том числе между
разными экземплярами Go-сервера. Транзакция обработки сообщения сохраняет общую атомарность.
Миграции схемы для этой возможности не требуются.

Интеграционные тесты: `internal/integration/meeting_conflicts_test.go`. Проверяются границы,
часовые пояса, перенос, отмена/удаление, чужие записи, одновременные запросы, подтверждение,
новые конфликты после предупреждения и составные команды.

Вопрос о конфликте содержит названия и интервалы встреч в часовом поясе пользователя.
